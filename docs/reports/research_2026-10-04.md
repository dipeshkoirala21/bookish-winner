### Recommendations (researcher + verifier)

- Stay on Unity 6 with URP; do not switch to Godot. Godot 4.7 C# export is still experimental on both Android and iOS, it has no built-in terrain, double precision needs custom export templates, and there is no shipped large 3D open-world Godot mobile precedent. Unity has the needed licensing (free under $200K, no Runtime Fee, optional splash), mobile requirements and CI images today.
- Pin the project to Unity 6.3 LTS (6000.3.x; latest is 6000.3.25f1, supported to Dec 2027). Do not use 6000.0 (EOL Oct 2026) or the short-lived Supported releases 6.4, 6.5 and 6.6. Re-evaluate moving to 6.7 LTS a few patches after it ships (late 2026 or early 2027), and treat Unity 7 (CoreCLR) as a 2027+ migration.
- Write C# core and gameplay code as plain .NET-Standard-style C# (no Mono-specific APIs, no reliance on InstanceID semantics) so the CoreCLR/Unity 7 transition is cheap.
- Rendering: URP Forward+ with GPU Resident Drawer and GPU occlusion culling only on the Vulkan/Metal tier. Keep a GLES 3.1 fallback quality tier (GLES 3.0 is dropped from 6.6). Build terrain as chunked MeshRenderer meshes generated from the Copernicus DEM, not the Unity Terrain component, so it benefits from GPU Resident Drawer/BRG. Profile whether GPU occlusion culling helps Nepal's mountain scenes before enabling it.
- Use Burst plus the Jobs system (stable on Android ARM64 and iOS ARM64) for tile decoding, meshing and LOD. Do not take a hard dependency on Entities/Entities Graphics for v1. On 6.3 they are the 1.x line, and 6.4+ moves them into versioned core packages with API changes (EntityId 8-byte, managed components deprecated).
- CI: GameCI unity-builder (pin a major version, e.g. v4.8.2/v5.0.1 or v6) on ubuntu runners with unityci/editor 6000.3.x android and ios images builds the Android AAB and the iOS Xcode project. A macOS runner with fastlane signs and uploads the IPA. Use a Personal .ulf secret for now, with Unity Build Automation's free 100 Mac minutes per month as a supported fallback for iOS.

### Recommendations (researcher + verifier)

- Use one self-hosted delivery path on both platforms as the baseline: Unity Addressables with Build Remote Catalog on, one Addressables group per region (labels like region:kathmandu-valley, region:pokhara) with Remote build and load paths, hosted on a CDN. Prefer Cloudflare R2 with a custom domain (no egress fees) or Unity CCD (50GB a month free, then $0.08/GB). This works the same on iOS 16+ and Android 10+, needs no store review for data updates, and is allowed by App Store 2.5.2 and Play's Device and Network Abuse policy because the packs are data, not code.
- Keep the base install at 150MB or less on both stores, and in any case under 200MB. That avoids Play's mobile-data size dialog and iOS's 'Ask If Over 200 MB' cellular prompt. The base install should hold code, UI, shaders, a coarse whole-Nepal overview (for example a downsampled DEM and WorldCover, plus a simplified OSM layer for the map and search index) and one small starter region bundled locally, so the game is playable offline at first launch.
- Split each region into AssetBundles of about 64MB or less (Unity's guidance) so downloads resume and update in small pieces. Use 'Prevent Updates' on the large static groups (terrain heightmaps, landcover textures) and keep OSM-derived vector or POI layers in separate, smaller groups that can be updated often. Archive addressables_content_state.bin for every released build and platform in CI.
- Before downloading any region, call Addressables.GetDownloadSizeAsync and show the size with a Wi-Fi recommendation and an explicit cellular opt-in. This satisfies Guideline 4.2.3(ii) and suits Nepali users on mobile data. Download with DownloadDependenciesAsync, show progress, allow pause and resume, offer a 'delete region' option, and call Addressables.CleanBundleCache after catalog updates.
- Version catalogs per app version, for example by putting the app version or a content hash in the remote catalog URL, and keep N-1 catalogs live on the CDN so older clients keep working. Turn on bundle CRC checks for remote groups.
- Do not use iOS On-Demand Resources (deprecated in iOS 27) or Unity's OnDemandResources API.
- Optional on Android only: use Addressables for Android 1.1 to ship the starter region as a fast-follow PAD pack, not install-time, which needs 2x disk space during install. Free Play hosting can be added later for on-demand region packs (up to 1.5GB each, 100 packs, 30GB total). Expect a mobile-data consent dialog for packs over 200MB, and keep the CDN path as the fallback for sideloaded or non-Play installs.
- Optional on iOS 26+ only: Apple-Hosted Background Assets through Apple's official Unity Background Assets plug-in (WWDC26, Xcode 27, Unity 2022 LTS or later) gives free hosting (200GB, 200 packs) and pre-launch prefetch. - **[high]** ODbL 1.0 s.1 defines a Produced Work as: "a work (such as an image, audiovisual material, text, or sounds) resulting from using the whole or a Substantial part of the Contents (via a search or other query) from this Database, a Derivative Database, or this Database as part of a Collective Database." ### Recommendations (researcher + verifier)

- Attribution UX, following the OSMF games and interactive-maps safe harbour: (1) A startup splash with 'Map data © OpenStreetMap contributors' that is legible, WCAG contrast, and shown for at least 5 s or until dismissed. (2) A persistent small corner credit 'OpenStreetMap' on the full-screen map and minimap, linked or tappable to openstreetmap.org/copyright, which may collapse to an (i) button. (3) A 'Data licences' / Credits screen reachable from the main menu with the full texts below. (4) The same texts on the store listing or website legal page.
- Verbatim credits block for the Data licences screen. OSM: 'Contains information from OpenStreetMap (openstreetmap.org/copyright), which is made available here under the Open Database License (ODbL) (opendatacommons.org/licenses/odbl/1-0/).' Copernicus DEM: 'produced using Copernicus WorldDEM-30 © DLR e.V. 2010-2014 and © Airbus Defence and Space GmbH 2014-2018 provided under COPERNICUS by the European Union and ESA; all rights reserved'. WorldCover: '© ESA WorldCover project 2021 / Contains modified Copernicus Sentinel data (2021) processed by ESA WorldCover consortium — licensed CC BY 4.0 (creativecommons.org/licenses/by/4.0/); resampled and stylised for this game.' Fonts: the OFL copyright lines plus the OFL 1.1 text for Baloo 2, Mukta and Noto Sans Devanagari, using the OFL.txt shipped with the exact binaries.
- Put the Copernicus liability sentence in the EULA or legal notice, as Copernicus Art. 6(c) requires: 'The organisations in charge of the Copernicus programme by law or by delegation do not incur any liability for any use of the Copernicus WorldDEM-30'. Do not use the Copernicus or ESA logos, and do not imply endorsement.
- Satisfy ODbL 4.6 and 4.7(b) proactively. Publish the data pipeline (method), the pinned OSM snapshot ID and timestamp, and any hand-edited OSM correction files under ODbL at a public URL such as a GitHub repo or release. Optionally also publish the game-ready OSM-derived database itself. This covers both the 'Produced Work from a Derivative Database' duty and any argument that encrypted or DRM'd app bundles are a Restricted Database. Prefer contributing real data fixes upstream to OSM.
- Keep the OSM, DEM and landcover layers independent, per the Collective Database and Horizontal Layers guidelines. Do not write DEM-derived values or WorldCover classes into OSM feature records in the shipped database. Do not fill gaps in OSM forest, landuse or water with WorldCover polygons of the same feature type. Combine them only at render or runtime, and record in ARCHITECTURE which feature types come from which source.
- Ingest OSM without personal metadata. Either use Geofabrik's public nepal-latest.osm.pbf, or strip user, uid and changeset fields from the geo2day file at the first pipeline step and verify that none survive in build outputs. Record the source URL, timestamp and MD5 in ASSET_MANIFEST. Treat geo2day's .poly boundary as non-authoritative.
- Do not use HydroRIVERS or HydroSHEDS v1 in shipped content, because of the WWF EULA flow-down, anti-decompile clause, indemnity, termination at WWF's discretion and conflict with ODbL publication. Derive rivers from OSM waterways plus in-house flow accumulation on Copernicus GLO-30. If HydroRIVERS is used at all, limit it to internal QA comparison, which is not public use, and get legal sign-off before shipping anything derived from it. Revisit HydroSHEDS v2 (CC-BY 4.0) when Asia is released.
- Use NASADEM or SRTMGL1 only as a CC0 or public-domain fallback or void-fill. Credit them as a courtesy ('NASADEM_HGT v001 courtesy of NASA LP DAAC, doi:10.5067/MEASURES/NASADEM/NASADEM_HGT.001'). Note that mixing them into Copernicus-derived terrain still requires the Copernicus 6(b) notice.
- Fonts: bundle the TTFs or TMP SDF atlases freely in the Unity build, include the OFL.txt and copyright lines in the licences screen and under StreamingAssets/licenses, and never sell or offer the fonts as a separate DLC item. Subsetting is allowed (no Reserved Font Names declared), but the result stays under OFL.
- QA viewer and the OSM tile server: only for interactive human use by developers. Set a custom User-Agent such as 'GhumanteQA/0.1 (+contact URL/email)', keep the default browser cache (7 days or more), and show attribution. Never prefetch, run automated screenshot sweeps, work offline, or reference tile.openstreetmap.org from the shipped game. Better still, serve the QA viewer from Ghumante's own vector or raster tiles built by the pipeline (for example PMTiles), and keep the OSM tile URL configurable.
- Create a machine-readable LICENSES / attribution manifest per source: source URL, version or release, retrieval date, licence, verbatim notice, and where it is displayed in game. Add a CI check that fails if a new data source lacks an entry.
- Implement an OSM credit that fits the games safe harbour. Show a startup splash with "© OpenStreetMap contributors" or "Map data from OpenStreetMap" plus the printed URL openstreetmap.org/copyright. Keep it visible at least 5 s unless the player dismisses it. Add a persistent '(i)' in a corner of the world map and minimap, and a 'Data licences' menu entry with the full notices. Show the URLs as plain text in-game: ODbL 4.3a says hyperlinks 'should' be replaced by plain URIs where links are not possible.
- Put these Copernicus notices verbatim in the credits and EULA or legal notice: Art.6(b) "produced using Copernicus WorldDEM-30 © DLR e.V. 2010-2014 and © Airbus Defence and Space GmbH 2014-2018 provided under COPERNICUS by the European Union and ESA; all rights reserved" and the Art.6(c) disclaimer sentence. Do not use Copernicus, ESA or Airbus logos or imply endorsement. Under the termination clause, a missing notice can end the licence.
- Add the WorldCover line "© ESA WorldCover project 2021 / Contains modified Copernicus Sentinel data (2021) processed by ESA WorldCover consortium" (if using v200) and cite DOI 10.5281/zenodo.7254221.
- Keep DEM and WorldCover data out of OSM feature attributes and out of the OSM-derived runtime database. Use them only as separate terrain and landcover layers (Horizontal Layers / Collective Database). Do not fill OSM gaps from them, for example forests from WorldCover or peak ele from the DEM. Document the feature-type separation in LICENSES.md.
- Open-source the OSM-to-runtime pipeline, which the LWG accepted as satisfying ODbL 4.6(b) in the Organic Maps issue (2025-10-06). Also publish, free of charge, an ODbL download of any OSM-derived database in the bundle (4.6a). State the offer in the credits and on the legal page instead of waiting for requests.
- Ship a LICENSE/README (ODbL URI plus attribution) next to OSM-derived data files in the bundle, per ODbL 4.2b/4.2d. Do not encrypt or obfuscate OSM-derived data mainly to prevent extraction. If asset bundles must be encrypted, provide an unrestricted parallel copy (ODbL 4.7b).
- Confirm the DEM source is the GLO-30-F / 'Public' instance, never GLO-30-R, whose terms limit public display to non-commercial use. Pin the actual release in ASSET_MANIFEST (the AWS s3://copernicus-dem-30m bucket is the 2021 release with Sinergise's edge-trimmed COGs, not 2024_1). Archive the licence PDF, tile list and checksums, because CDSE says maintenance runs only 'until 2026'.
- Re-check the OSMF Attribution Guideline revision history before each release. The only 2024-2026 edits were cosmetic (2026-09-10), but OSMF reserves the right to ask for different attribution later.

### Open risks

- LAWYER: Whether OSM-derived vector, routing or search-index data inside the app bundle is 'Conveyed' as a Derivative Database (triggering ODbL 4.2 notices inside the data files, the 4.4 ODbL licence, and 4.7 technological-measure limits given app-store DRM and encrypted Addressables) or is only part of a Produced Work. The Produced Work Guideline points to 'intended for extraction' as the test, but the line is untested.
- LAWYER: Licence compatibility if any non-OSM content ends up inside the ODbL Derivative Database. Copernicus DEM is 'all rights reserved' with flow-down obligations in Art. 6(c) and 6(e); WorldCover is CC BY 4.0 with attribution and no-DRM terms; HydroSHEDS v1 is under the WWF EULA. Under ODbL 4.4(d), incompatible content must not be added. Layer separation reduces but does not eliminate this risk.
- The Trivial Transformations guideline is internally inconsistent: the page says 'at the proposal stage' while the index lists it as board-endorsed. It also excludes any transformation that uses other data sources, so DEM-based processing of OSM geometry (for example road grading or bridge heights written back into the data) is outside its safe harbour.
- The Copernicus DEM licence never explicitly says 'commercial'. Commercial use is inferred from the free, worldwide, unrestricted grant to 'any natural or legal person'. Art. 6(e) requires binding Subsequent Users if Ghumante grants redistribution rights, which may be needed if terrain data is published alongside ODbL outputs. The EULA needs a flow-down clause, which a lawyer should check.
- HydroSHEDS v1 WWF licence: EULA flow-down, anti-decompile, indemnification, termination at WWF's sole discretion, and DC governing law. HydroSHEDS v2 (CC-BY) covers only the Americas as of 2026-10-04, and no release date for Asia was found.
- Personal data: the geo2day extract includes contributor names, uids and changesets. Processing or shipping them could raise GDPR or UK GDPR issues and conflicts with OSMF's approach of offering dumps without that data. Mitigate by stripping at ingest. geo2day has no published terms of service and has no OSMF affiliation, so provenance and continuity are unverified.
- Not researched here, but legal and political: depicting Nepal's borders (for example the Kalapani/Lipulekh/Limpiyadhura area, which Nepal and India dispute) in a commercial game distributed in India, Nepal or China app stores may carry regulatory or market risk. OSM data and the geo2day .poly boundaries are not authoritative. Needs a lawyer or local-market review.
- The OSMF says its attribution guidelines may change ('compliance today does not mean that we will not propose or ask for different attribution guidelines in the future'). The tile usage policy can also change or block access without notice. Re-check both before each release.
- Unverified: the exact osmium flags for metadata stripping, and whether Unity 6 TextMeshPro or UI Toolkit correctly shapes Devanagari conjuncts with these fonts. That is a rendering issue, not licensing, but it affects the font choice.
- Font copyright lines differ between the Google Fonts and upstream Ek Type distributions. Ship the notice that matches the exact binary used, or include both.
- Whether Copernicus DEM (or CC BY 4.0 WorldCover) content is 'compatible' under ODbL 4.4d is unresolved. I found no OSMF/LWG ruling. The risk becomes real only if DEM or WorldCover values are merged into OSM-derived databases.
- Whether Ghumante's bundled vector, routing or search files are Produced Works or Derivative Databases is unsettled. The 2025 Organic Maps complaint argued that mixed OSM plus elevation vector files are Derivative Databases, but the LWG did not formally rule on that point.
- There is a tension inside the Attribution Guideline: the general rule says attribution should not require interaction, while the games section allows credits-page or menu attribution. A credits-only design is ambiguous.
- The Trivial Transformations page still says 'proposal stage' while the index says the guidelines are board-endorsed. Its protection also lapses when changes are made 'with the prime motive of preventing access', which bears on encrypted asset bundles.
- Unknown: whether app-store platform DRM (e.g. iOS FairPlay on the binary) counts as a 'technological measure' on the database under ODbL 4.7a. No primary source addresses this.
- Copernicus DEM is stated to be 'maintained until 2026'. Future distribution channels, releases and licence terms after 2026 are unknown.
- The Copernicus 'Non-released tiles' spreadsheet (spacedata.copernicus.eu) failed to download (connection reset). I verified Nepal coverage through the AWS GLO-30 Public tileList.txt instead.
- OSM enforcement is active in 2026: local chapters and the LWG have considered app-store removal requests against mobile apps that lack attribution.

### Recommendations (researcher + verifier)

- Use Unity 6.3 LTS (supported to Dec 2027) as the baseline, not 6.0 LTS, whose support ends October 2026. Build with targetSdk 36, minSdk 29 and 16 KB page alignment, and confirm the chosen 6.3 patch supports API 36 before the Nov 1, 2026 extension deadline.
- Question 2, whether 1.5 GB is safe on 3-4 GB Android. It is NOT safe on 3 GB devices. It sits at the top of the old 1/4-1/2-of-RAM rule (0.75-1.5 GB) and equals the lowest Android 17 Memory Limiter visible cap (1/2 of 3 GB = 1.5 GB). Usable RAM on '3 GB' phones is also lower. It is acceptable but tight on 4 GB devices: about 0.75 GB under the Play vitals games foreground threshold (2.25 GB Anon RSS + swap) and within the Memory Limiter 2.0-2.7 GB band. Recommended: 3 GB Android at 0.9-1.0 GB peak total footprint; 4 GB Android at 1.3 GB typical and 1.5 GB hard peak; 6 GB+ Android at 1.8-2.0 GB peak.
- iOS budgets. On 4 GB iPhones (iPhone 11/12/13, A13-A15) use 1.4 GB peak footprint, about 67% of the reported 2098 MB jetsam ActiveHard limit; on iOS, Metal/GPU resources count toward the footprint because memory is unified. On 3 GB devices (XR, SE 2nd gen, X, 8 Plus) use 1.0-1.1 GB. On 6 GB+ devices use 2.0 GB. Add the increased-memory-limit entitlement, but do not budget on it. At startup and every 10-30 s, read os_proc_available_memory() and lower the texture and streaming tier when it drops below 400 MB.
- Device tiers. LOW: Helio G85/G99, Unisoc T606, Mali-G52/G57 MC1-2, 3-4 GB, GLES 3.x or Vulkan 1.1. MID: Snapdragon 7 Gen 1/7s Gen 2 (Adreno 644/710), 6-8 GB. MID-HIGH: Snapdragon 7 Gen 3 (Adreno 720). HIGH: A14+ such as the iPhone 12, and SD 8-series. Classify at first launch using GPU name, ActivityManager.MemoryInfo.totalMem and SystemInfo.graphicsDeviceType, then refine with a 10 s frame-time probe.
- Frame-rate targets. LOW: 30 fps locked at render scale 0.65-0.75. MID: 30 fps default with an optional 40/45 or 60 fps mode on 7 Gen 3-class devices. HIGH: 60 fps with dynamic resolution, dropping to 30 fps on thermal 'serious' (iOS) or headroom ≥0.8 (Android). Set Application.targetFrameRate explicitly, because -1 means 30 fps on mobile.
- Draw-call and triangle budgets. These are engineering estimates from the 3DMark ratios and Meta's Quest numbers, not vendor figures; validate them on devices. LOW: ≤80-120 SRP batches, ≤100-150k visible triangles (≤100k on T606/G85), 1 cascade 512-1024 shadow or blob shadows only, no post-processing beyond a tonemap/LUT. MID: ≤150-200 batches, 250-400k triangles, 1-2 cascades at 1024. HIGH at 60 fps: ≤200-300 batches, 400-700k triangles; at 30 fps up to 1M triangles.
- Rendering path. Default to URP Forward (not Forward+) with the SRP Batcher on, static batching for building chunks generated from OSM, and GPU instancing or custom BatchRendererGroup for trees, rocks and grass, which also works on GLES. Test the GPU Resident Drawer (Forward+, Vulkan/Metal only) as an opt-in on the HIGH tier, and adopt it only if device profiling shows a net gain, given the Forward+ GPU cost on Android (UUM-40387). Keep a GLES 3.x fallback for the roughly 11% of handheld devices without Vulkan 1.1+.
- Textures. Use ASTC only: 6x6 for terrain and building albedo, 8x8 for distant or low-tier textures and normal maps, 4x4 for UI and character faces. Turn on mipmap streaming with a memory budget per tier (LOW 192-256 MB, MID 384 MB, HIGH 512 MB). Keep Read/Write disabled, and disable mipmaps on UI to save about 33%.
- Map streaming. Hard-cap resident terrain and OSM tiles per tier (for example LOW 3x3 tiles, HIGH 5x5), evict ahead of loads, and reuse pooled meshes so Unity's native heap does not keep growing. Unity keeps grown heaps, so peak memory during tile transitions is what triggers the Memory Limiter or jetsam.
- Thermal. Turn on Unity Adaptive Performance (built-in from 6.3) with the Android (ADPF) and Apple providers. Design 60 fps modes to fit in about 10-11 ms of GPU time, roughly 65% of 16.6 ms, because the iPhone 12 holds only 73-77% of peak in 3DMark stress tests. On Android 10 (API 29) there is no thermal headroom API, so scale from thermal status and frame-time trends.
- Telemetry and gates. Log ApplicationExitInfo descriptions on Android (look for 'MemoryLimiter:AnonSwap'), MetricKit peak memory and jetsam reports on iOS, and RssAnon+VmSwap per RAM bucket. Release gates: user-perceived LMK rate under 1%, P90 foreground memory under the vitals threshold minus 25%, and a 20-minute sustained-play soak on one LOW, one MID and one HIGH reference device (for example a Helio G85 3 GB, a 7s Gen 2 6 GB and an iPhone 12).
- Consider raising the iOS minimum to iOS 17 (XS/XR and later) if early testing shows A11 devices (iPhone 8/8 Plus/X, the oldest iOS 16 targets) cannot hold the LOW-tier budget. Apple's App Store data suggests the extra reach from iOS 16 is small in 2026, but Apple does not report iOS 16 separately.
- Set the Android budget against the binding cap. On 4 GB-tier devices (MemTotal 3200-4800 MiB), keep foreground PEAK RssAnon+VmSwap at or below about 1.5 GB. The Android 17 visible memory.high is 2,048 MiB, which is below Play's 2.25 GB game threshold. Treat 2 GiB as a hard ceiling that must never be reached, even during tile or scene transitions.
- Phones in the 3 GB class (MemTotal under 3200 MiB) get neither a Memory Limiter cap nor a vitals threshold, but LMK still applies. Keep a lower tier there (about 1.0-1.2 GB) and size it from device telemetry, not from documented caps.
- For 4 GB iPhones (iPhone 12/12 mini/X/Xs), treat roughly 2.0 GB (the 2021 community figure of 2098 MB ActiveHard) as the kill ceiling and target a peak of 1.4-1.5 GB. Choose the texture and streaming tier at runtime from os_proc_available_memory(), polled and never cached.
- Ship with the increased-memory-limit and extended-virtual-addressing entitlements. Add a CI step that runs `codesign -d --entitlements` on the App Store/TestFlight IPA. Never count the extra memory in the base budget.
- Avoid in-process WebKit/JavaScriptCore (WKWebView-based ad or consent SDKs, JSContext) during gameplay. Test iPads on iPadOS 26.6 or later, given the 26.4/26.5 address-space regression.
- Do not rely on Unity Application.lowMemory on Android. Its documented triggers have not been delivered since API 34. With GameActivity, memoryUsageChanged reports only Critical. Instead, poll RssAnon and VmSwap from /proc/self/status (or ProfilerRecorder) every few seconds and degrade proactively. Also trim in OnApplicationPause with Resources.UnloadUnusedAssets.
- Android telemetry: at startup, read getHistoricalProcessExitReasons() and record REASON_MEMORY_LIMITER (SDK 37.2+), REASON_OTHER with 'MemoryLimiter:AnonSwap', and REASON_LOW_MEMORY separately, along with ActivityManager.MemoryInfo.totalMem so data can be bucketed by vitals RAM tier.
- iOS telemetry: use MXMetricManager for peak and suspended memory on iOS 16-26, and MetricManager/MemoryExceptionDiagnostic on iOS 27+. Compute P50 and P90 per device model on the backend.
- QA on a 4 GB and a 6 GB Pixel running Android 17. Use `adb shell am memory-limiter status` to confirm the caps, and `am memory-limiter manual <pid> 2GB` to simulate the 4 GB tier cap on larger devices.
- Because Unity holds on to peak memory, avoid spikes: use small per-region Addressables bundles, background music set to Streaming, ASTC textures, Read/Write off, mips off for UI, IPreprocessShaders stripping of URP variants (4 MB chunk decompression), and object-pool flushes on region change.
- Run offline map-pack downloads and unzipping in a separate Android ':downloader' process so their buffers never count against the game process limit.
- Release gates: user-perceived LMK rate below 1%; P90/P50 memory ratio below 3.5x per process; under the vitals thresholds before February 2027.

### Open risks

- Apple publishes no jetsam limits. The iPhone 12 figure (ActiveHard 2098 MB) is a 2021 community report and may have changed in iOS 16-26. No verified limits were found for 3 GB iPhones (XR, SE 2nd gen, X, 8 Plus) or for 3-4 GB iPads (e.g. iPad 9th/10th gen), so they must be measured with os_proc_available_memory() on real devices.
- Which device models the increased-memory-limit entitlement actually raises, and by how much, is undocumented. Do not plan around it.
- Android 17 Memory Limiter limits are set by each OEM, cannot be queried at runtime, and are rolling out over the next year. It is unknown whether 3 GB devices will be covered, or what caps OEMs will pick within the 1/2-2/3 recommendation.
- It is unclear whether GPU and driver allocations on Adreno/Mali (dmabuf/kgsl) count in the vitals 'Anonymous RSS + Swap' metric. Unity's real footprint compared with what Play measures has to be checked with Perfetto on device.
- Play vitals memory thresholds become a store-visibility and publishing factor from February 2027. The exact aggregation (which percentile, share of sessions) for enforcement is not fully specified in the docs fetched.
- The Android page carrying the 'games use 1/4-1/2 of RAM' guidance now returns 404, so that rule is only confirmed through search snippets and may be superseded.
- There are no official triangle or draw-call budgets for phones from Unity, Google, Apple or Arm. The budgets above are estimates scaled from 3DMark medians and Meta Quest guidance and need device profiling.
- 3DMark figures are UL median user submissions. Thermal stability varies a lot by phone chassis: a secondary review reported about 58% Wild Life Extreme stress stability on one Snapdragon 7 Gen 3 phone, while UL lists 98-99% on others.
- The Unisoc T606 GPU core count is inconsistent across sources (Mali-G57 MP1 vs MC2), and no Unisoc primary spec page could be fetched.
- Forward+ cost on Android (UUM-40387) was measured on 2022.3/2023.2 and may have improved in Unity 6.3. GPU Resident Drawer behaviour on mobile Vulkan, and reported BRG rendering bugs on some Mali GPUs, were not verified for 6.3.
- Android version share comes from Google's Dec 2025 Android Studio data via a secondary outlet (heise). Nepal-specific Android and iOS shares, and the device mix such as the share of 3 GB phones, are unknown and should come from Play Console 'Reach and devices'.
- It has not been verified which Unity 6.3 LTS patch officially supports targetSdk 36 and 16 KB pages. Check the release notes before the Nov 1, 2026 target-API extension deadline.
- The iPadOS 26.4-26.5 address-space regression (WebKit/JSC) shows the per-app memory limit can change between OS point releases. Re-test budgets on every major iOS release.
- Google has not published which percentile (P50, P90, P99?) or what share of users is compared against the memory thresholds. The 26 Aug 2026 blog says 'additional details will be provided later this year', and thresholds may 'adapt over time'.
- It is unverified whether GPU or driver allocations (Unity textures and meshes uploaded via Vulkan/GLES, dma-buf, kgsl or mali) are charged to the Memory Limiter's cgroup memory.high or to RssAnon. Android's overview says the footprint metric excludes GPU-private memory, but per-SoC behaviour must be measured.
- Android's own documents disagree on kill behaviour. The Unity guide says 'immediately terminated', while AOSP and the blog describe throttling and zRAM first, then a kill after swap runs out. Real devices need testing.
- OEM rollout of the Memory Limiter is 'over the coming year'. OEMs might ship non-standard memory-limiter-config.xml values, even though AOSP stresses uniform limits.
- iOS per-device jetsam limits are undocumented. The only concrete figure (2098 MB on 4 GB iPhones) dates from 2021 and may differ on iOS 16 to 27.
- The JavaScriptCore address-space regression may affect iOS 18.x devices (one iOS 18.7.10 report, not confirmed by DTS). Third-party ad or consent SDKs may load WebKit without the team realising.
- Apple's 'iOS 13.0 - 27.2' availability range for MXMetricManager/MXMemoryMetric suggests deprecation, but no deprecation text was found. The timeline for removing support is unknown.
- Unity could change the Android Application.lowMemory mapping in a future 6.x release. The 6.4 docs still map it to callbacks Android no longer delivers.
- The 'onTrimMemory can cause deadlocks in Unity' claim has no detailed explanation in the linked Android pages, so the root cause and affected Unity versions are unknown.
- The '1/4 to 1/2 of physical RAM' guidance for games now exists only in search snippets and an archived snapshot I could not fetch. Do not cite it as current.

### Recommendations (researcher + verifier)

- Use a two-tier horizontal scale modelled on ETS2/ATS: PLACES (city cores, villages, landmark precincts, trek villages) at 1:4 linear (allow 1:3 for very dense cores such as Thamel, Patan and Bhaktapur Durbar Squares), and CORRIDORS (highways, rivers, trails between places) at 1:20 linear. 1:20 is the only primary-source-confirmed precedent (ATS since 2016, equivalent to ETS2). Document both ratios in ARCHITECTURE and keep them constant across all regions; SCS's 2025 UK rework shows the cost of mixed regional scales.
- Do not scale geometry uniformly. Compress the OSM road/trail graph by edge (corridor edges x1/20, place-internal edges x1/4) and blend at place boundaries, as ETS2 does at city edges. Keep topology and the order of junctions and landmarks so real routes such as Kathmandu-Mugling-Pokhara stay recognisable.
- Use a separate vertical scale. With horizontal 1:20, a 1:20 vertical turns Everest into about 442 m and flattens the Himalaya. Recommend a vertical factor of about 1:6 to 1:8 on corridors (2.5-3.3x slope exaggeration, cartoon-friendly), with per-region base-elevation offsets and a slope clamp. Inside 1:4 places use a vertical close to 1:4 so streets and ghats keep plausible gradients. These numbers are design proposals, not sourced facts.
- Resulting sizes, derived from sourced inputs: all of Nepal at 1:20 would be about 369 km2 and about 40-42 km end to end. Kathmandu Valley at 1:4 is about 40 km2 (about 7.5 x 6.25 km), roughly half of FH4's 71 km2. Thamel to Boudhanath becomes about 1.2 km. Kathmandu-Pokhara (about 200 km road) becomes about 10 km of corridor. Lukla-EBC trail (65 km) becomes about 3.3 km at 1:20, or 6.5 km at 1:10 if the trek warrants special treatment. Ship regions, not the whole country: M1 should be the Kathmandu Valley only.
- Treat the long-haul links (Kathmandu-Pokhara, Kathmandu-Chitwan, Kathmandu-Lumbini, Kathmandu-Lukla flight) as optional playable 1:20 corridors plus bus/flight fast travel, rather than requiring continuous driving. The Crew's 90 minute coast-to-coast showed that long traversals work for car fans but not for casual mobile sessions.
- Tie in-game time compression to the corridor scale, as SCS did, so 'a day's bus ride' feels proportionate. Show real-world facts (real km, real days for EBC) on a info card in the UI rather than simulating them.
- Compression makes the source data effectively finer: GLO-30 at 1:4 means about 7.5 m in-game post spacing, and WorldCover 10 m at 1:20 means about 0.5 m per in-game cell. Use this headroom for smoothing and stylisation instead of fetching higher-resolution DEMs.
- Stay offline-first and own the pipeline. Google Map Tiles policies forbid caching, offline use and deriving 3D objects. Niantic's and Microsoft's Unity map SDKs were sunset in 2024-2025, Mapbox Unity v2 is no longer developed, and The Crew became unplayable when its servers closed in 2024. Use Cesium for Unity (Apache-2.0, supports Unity 6, iOS and Android) only as an optional self-hosted 3D Tiles viewer for QA, not as the runtime world source.
- Boundary import: provinces = admin_level 4, districts = 6, local levels = 7, wards = 9. Clip to relation 184633, normalise name:suffix into the 4 official types, and add a QA test asserting 7 / 77 / 753 / 6,743 with a tolerance list for the known OSM gaps (749 level-7, 6,741 level-9 in the 2026-10 extract).
- Validate and clamp OSM numeric tags (building:levels, height, ele) before mesh generation, as the MSFS 212-floor incident shows. Never ask or reward players for editing OSM (Pokemon GO precedent).
- Cite only primary sources for scale ratios in planning documents. The ATS/ETS2 1:20 figure has a primary SCS blog source (23 Jun 2016). Label 1:19/1:15/1:3 as 'secondary report of an unlinked SCS forum post (racinggames.gg, Sep 2026)'.
- Drop the '1:36' The Crew figure. Present The Crew as about 5,000 km2 (developer-stated) and about 1:40 linear (derived), and note that measured coast-to-coast drives were about 40-45 minutes against a 90-minute developer claim.
- Correct the 10,000 km road quote to Ahmed Boukhelifa (Ivory Tower COO, OPM, Jun 2013). Keep Gerighty's Apr 2014 New York/Liberty City comparison.
- Correct the 212-floor tower to MSFS 2020 (Aug 2020). Add a pipeline validation rule that clamps building:levels and height (for example a per-district maximum, outlier rejection against neighbours) and logs rejected values for QA.
- Update LICENSES.md: OSM2World is MIT since 13 Feb 2026 (not LGPL). Record the commit SHA 92f2492299ba705d2863215acfe2826797812d07 as provenance.
- Choose non-uniform compression: highway and trail corridors at about 1:20 to 1:30 (the ATS rescale shows 1:35 felt too compressed), towns and landmarks at 1:1 to 1:3. Treat vertical exaggeration or compression as a separate, explicit parameter, because Nepal's relief (60 m to 8,848 m) does not fit a horizontal ratio.
- Set traversal-time targets (for example an end-to-end Mahendra Highway drive) and measure them in playtests. Do not rely on press-quoted times, which overstated by up to about 2x in The Crew's case.
- Ship region by region (as Motorfest did with Season 9's Kaho'olawe in Mar 2026) rather than the whole country at launch.
- Keep the world fully offline with no runtime map SDK or streaming dependency (Mapbox v2 frozen, Niantic SDK off Oct 2025, Microsoft service off Mar 2025, Google tiles prohibit offline use and caching).

### Open risks

- The ETS2 city scale (about 1:3) and UK scale (1:15) are confirmed only by a secondary article quoting an SCS forum post. Only the 1:20 corridor figure is primary-sourced.
- Official km2 figures for GTA V, FH5, FH6 and The Crew 2/Motorfest are not published. Benchmarks in the docs must be labelled as estimates.
- Disputed border: Nepal's 2020 map includes Limpiyadhura-Lipulekh-Kalapani (147,516 km2). I did not verify which claim OSM relation 184633 follows in that area. Showing the 'wrong' border is politically sensitive in Nepal and in India, which affects store approval and reputation. Check this before any map UI ships.
- Nepal's lowest point is contested: Kechana Kalan at 60-70 m against Mukhiyapatti Musaharniya at 59 m. I found no Survey Department primary source.
- Road distances and drive times are volatile and differ by source: Kathmandu-Lumbini is 272 or 325 km, Prithvi Highway 4-laning is unfinished, and the 2026 floods damaged roads. Compute in-game distances from the OSM graph snapshot and avoid hard-coded 'real time' claims.
- Two-tier scaling creates distortion at place/corridor seams: road curvature, river widths and the line of sight to peaks such as Machhapuchhre from Pokhara. Prototype the blend on Kathmandu Valley before committing.
- The vertical exaggeration and slope clamp values are design proposals. They need a playtest for traversability, camera feel and character controllers, plus a check that famous viewpoints such as Sarangkot and Kala Patthar keep their skyline composition.
- Precise Lukla-EBC, Annapurna Circuit and Kathmandu Valley figures come from trekking operators, Wikipedia or a 1989 paper rather than an authoritative government source. Medium confidence only.
- The original SCS forum post for 1:19/1:15/1:3 was not located, so these ETS2 numbers are still unverified at the primary level.
- I could not fetch the Digital Spy (26 Jul 2014) source for the 40-minute The Crew crossing (domain blocked). The 45-minute figure rests on Wikipedia's citation.
- No official km2 exists for FH4, FH5, FH6, GTA V or Motorfest. All area benchmarks are community estimates.
- The Motorfest offline mode status after Mar 2026 is unknown (web search budget exhausted, so I could not check Apr-Oct 2026).
- The FH6 'Tokyo 5x Guanajuato' figure and the 220-246 km2 total are unverified in primary sources.
- OSM2World's MIT relicence covers the code. Its derived outputs and the hosted renderings (CC BY-SA 2.0) still carry OSM/ODbL obligations, and the OSM wiki is stale (still says LGPL).
- I could not verify the FH5 '1.5x' claim directly in the original IGN piece. It is relayed by GamePressure.
- Microsoft/Asobo have never officially documented how FS2024 uses OSM. The forum claim is from a user.

It can be read anonymously without an AWS account and is managed by Sinergise. The registry says there are no regular updates, except that GLO-30 Public may change if the list of public tiles changes. — [source](https://registry.opendata.aws/copernicus-dem/)
- **[high]** Tile folders are named Copernicus_DSM_COG_10_N27_00_E085_00_DEM/ ('10' is the 1-arcsec GLO-30 code; '30' is used for GLO-90). The name gives the south-west corner, so N27 E085 covers 27-28N, 85-86E. Each folder holds <name>.tif, an ISO 19115 XML, AUXFILES/{EDM,FLM,HEM,WBM}.tif plus ACM.kml, INFO/eula_F.pdf and PREVIEW quicklooks. All objects in the N27E085 folder have LastModified 2022-05-09. The bucket root tileList.txt lists 26,450 tiles. — [source](https://copernicus-dem-30m.s3.amazonaws.com/?list-type=2&prefix=Copernicus_DSM_COG_10_N27_00_E085_00_DEM/)
- **[high]** The AWS COGs are 3600x3600 float32 (deflate, 1024x1024 internal tiles, overviews 2/4/8, AREA_OR_POINT=Point, no nodata set). The first pixel centre sits exactly on the integer corner (85.0E, 28.0N). Per the AWS readme, the original DGED tiles are 3601x3601 and share one row/column with their neighbours. AWS removed the shared rows and columns on the east and south edges to make the sizes divisible by 2. — [source](https://copernicus-dem-30m.s3.amazonaws.com/readme.html)
- **[high]** GLO-30 uses horizontal datum WGS84-G1150 (EPSG:4326) and vertical datum EGM2008 geoid (EPSG:3855), in metres. Tile XML: 'horizontal: "WGS84-G1150"', 'vertical: "WGS 84 Geoid EGM08"'. — [source](https://dataspace.copernicus.eu/node/1306)
- **[medium]** Copernicus DEM release history on CDSE: 2019_1 (Dec 2019) up to 2021_1 (Jul 2021, negative-value correction), 2022_1 (Dec 2022, Norway/Spanish Pyrenees infill), 2023_1 (Dec 2023, Armenia/Azerbaijan/Moldova freed for GLO-30) and 2024_1 (Jul 2024, Spain tiles infill). No 2025 or 2026 release is listed. The AWS objects are dated 2022-05-09, so the AWS mirror predates 2022_1. The later releases only changed non-Nepal regions; that conclusion is my inference, and the exact AWS release label was not verified. — [source](https://dataspace.copernicus.eu/node/1306)
- **[high]** The GLO-30 licence (eula_F.pdf, shipped in each tile's INFO folder) grants worldwide, unlimited-time, free rights to reproduce, distribute, communicate to the public, and adapt/modify/combine. It has no non-commercial clause. When adapted, the required notice is: "produced using Copernicus WorldDEM-30 © DLR e.V. 2010-2014 and © Airbus Defence and Space GmbH 2014-2018 provided under COPERNICUS by the European Union and ESA; all rights reserved". — [source](https://copernicus-dem-30m.s3.amazonaws.com/Copernicus_DSM_COG_10_N27_00_E085_00_DEM/INFO/eula_F.pdf)
- **[high]** Product Handbook v5.0 (29.11.2022) mask codes. EDM: 0 void, 1 not edited, 2 infill of external elevation data, 3 interpolated, 4 smoothed, 5 airport, 6 raised negative, 7 flattened, 8 ocean, 9 lake, 10 river, 11 shoreline, 12 morphed, 13 shifted. FLM: 0 void, 1 edited (not filled), 2 not edited/not filled, 3 ASTER, 4 SRTM90, 5 SRTM30, 6 GMTED2010, 7 'SRTM30plus' (its footnote cites NASA SRTMGL1 v3 1-arcsec), 8 TerraSAR-X radargrammetric, 9 AW3D30, 100/102 Norway DEM v1/v2, 101 DSM05 Spain. HEM is a float32 height standard deviation, set to -32767 on edited pixels. WBM: 0 none, 1 ocean, 2 lake, 3 river. — [source](https://dataspace.copernicus.eu/sites/default/files/media/files/2024-06/geo1988-copernicusdem-spe-002_producthandbook_i5.0.pdf)
- **[high]** Mask shares I measured on AWS AUXFILES (EDM=2 means pixels infilled from external DEMs). N27E086 (Everest/Khumbu): 19.4% EDM=2, FLM fill sources SRTM30 8.8%, 'SRTM30plus' 8.6%, ASTER 1.6%, SRTM90 0.5%. N28E083 (Dhaulagiri/Annapurna): 31.9% EDM=2, SRTM30plus 17.3%, SRTM30 12.0%. N28E084 (Manaslu/Annapurna): 32.8% EDM=2. N27E085 (Kathmandu): 5.5% EDM=2. None of these tiles had void pixels (code 0). — [source](https://copernicus-dem-30m.s3.amazonaws.com/Copernicus_DSM_COG_10_N28_00_E084_00_DEM/AUXFILES/Copernicus_DSM_COG_10_N28_00_E084_00_EDM.tif)
- **[medium]** Every major summit I checked falls in EDM=2 infill. - **[high]** pyosmium 4.x API. Iterative style: osmium.FileProcessor(path, entities).with_locations(storage) (flex_mem default, or sparse_file_array / dense_file_array), .with_areas() (2-pass multipolygon assembly; area id = 2*way_id or 2*rel_id+1), .with_filter(f), .handler_for_filtered(h). Filters: EmptyTagFilter, EntityFilter, KeyFilter, TagFilter, IdFilter, GeoInterfaceFilter (adds __geo_interface__ for shapely). They run in order, and an object is dropped as soon as one filter rejects it. Handler style: SimpleHandler.apply_file(filename, locations=False, idx='flex_mem', filters=[]); implementing area() auto-enables area assembly. Do not keep references to OSM objects outside callbacks. Locally, a TagFilter pass over all Nepal nodes took ~6 s, and a KeyFilter('name') pass over the whole file ~8 s. — [source](https://docs.osmcode.org/pyosmium/latest/user_manual/04-Working-with-Filters/)

Strategies: simple (1 pass), complete_ways (2 passes, the default), smart (3 passes, complete multipolygons). — [source](https://docs.osmcode.org/osmium/latest/osmium-extract.html)
- **[high]** Unity TerrainData.heightmapResolution is clamped to 33, 65, 129, 257, 513, 1025, 2049 or 4097 (2^n+1). Neighbouring Terrain tiles join through 'Auto Connect' when they share a 'Grouping ID'. In Cesium quantized-mesh-1.0, vertices are quantized to 0..32767 with zig-zag delta encoding, indices use high-water-mark encoding, and each tile carries west/south/east/north edge-vertex lists so clients can 'add skirts to hide cracks between adjacent levels of detail'. — [source](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/TerrainData-heightmapResolution.html)
- **[high]** CDLOD (Strugar, Journal of Graphics, GPU, and Game Tools, 2009; MIT reference code) renders a quadtree of regular grid patches. A unified 3D-distance LOD function and vertex-shader morphing remove the need for mesh stitching. GPU geometry clipmaps (GPU Gems 2, ch. 2) use nested viewer-centred grids of odd size n=2^k-1 (typically 255), toroidal texture updates, vertex texture fetch for heights, and alpha-blended transition regions. — [source](https://github.com/fstrugar/CDLOD)
- **[medium]** Cesium for Unity is Apache-2.0, latest v1.26.0 (2026-10-01). Its changelog records iOS build support, an Android native library built with 16 KB ELF alignment for Android 15+ devices, and Unity 6.5 support (v1.25.0, 2026-08-03). Cesium's marketing page lists Windows, macOS, Android and VR but not iOS. — [source](https://raw.githubusercontent.com/CesiumGS/cesium-unity/main/CHANGES.md)
- **[medium]** The UN-recommended Nepali romanization (1972) shows 'no evidence of use either in Nepal or in international cartographic products'. Nepal's national mapping and NGIIP use the Nepal Survey Department (NSD) system, which uses diacritics (ā ī ū ṭ ḍ ṇ ś ṣ ṅ ñ ṁ). A simplified variant in use omits all diacritics (ṅ→ng, ṣ→sh), which is the 'conventional' map spelling style. The WGRS document (v4.0, Feb 2013) does not mention Hunterian. Hunterian (Hunter, 1871) was the Survey of India system for regions including Nepal. ISO 15919 and IAST are diacritic scholarly schemes; the current ISO status could not be checked because iso.org returned 403. — [source](https://arhiiv.eki.ee/wgrs/rom1_ne.htm)
- **[high]** Library versions and licences (PyPI, 2026-10-04): indic-transliteration 2.3.82 (2026-04-06, MIT), aksharamukha 2.3 (2024-10-14, GNU AGPL-3.0), rapidfuzz 3.14.6 (2026-08-30, MIT). Local test: indic-transliteration keeps the inherent schwa (ललितपुर→lalitapura, चितवन→citavana, काठमाडौं→kāṭhamāḍauṁ). aksharamukha with pre_options=['RemoveSchwaHindi'] and target RomanColloquial gives lalitpur, janakpur, dhulikhel, nagarkot, chitvan, bhaktapur, kathmadau. — [source](https://github.com/indic-transliteration/indic_transliteration_py)

### Recommendations (researcher + verifier)

- Use Copernicus GLO-30 from s3://copernicus-dem-30m as the only shipped DEM. Fetch the 45 tiles N26-N30 x E080-E088 together with their AUXFILES (EDM/FLM/HEM/WBM), record the S3 ETags in a manifest, and mosaic them through a GDAL VRT. That restores the east/south rows the AWS COGs dropped, before resampling into one continuous projected grid for all of Nepal.
- Add a summit/ridge correction pass. Take OSM natural=peak nodes with ele (3,345 available). Where EDM==2 near a peak, apply a smooth radial or Gaussian lift so the local maximum equals ele (Everest 8848.86). Then clamp slopes and despike pixels whose HEM is high or which come from SRTM90/GMTED fill. Log every change in a QA layer.
- Do not use FABDEM in the game (CC BY-NC-SA). Use AW3D30 v4.1 (free for commercial use, attribution per JAXA terms) or NASADEM only as offline QA references, or for a carefully blended patch on known-bad ridges. Never mix vertical datums.
- Bake terrain as 2^n+1 heightmap tiles (e.g. 257 or 513) with duplicated shared edge samples. Store heights as uint16 at about 0.15 m resolution over the 0-8,900 m range, plus a per-tile min/max header, with LZ4/zstd compression. Add skirts or edge stitching so different LODs meet without cracks. Prototype Unity Terrain first (Draw Instanced, Auto Connect, same Grouping ID). Fall back to a custom CDLOD-style quadtree with vertex-shader morphing if CPU or draw-call cost on mid-range Android is too high. Avoid adopting Cesium for Unity unless streaming real-world 3D Tiles becomes a goal.
- Fetch WorldCover v200 tiles N24/N27 x E078/E081/E084/E087 plus N30E078 and N30E081 (~1.05 GB). Downsample with mode/majority resampling, not bilinear, onto the terrain splat grid, treat 0 as nodata, and mind the pixel-area (WorldCover) vs pixel-point (DEM) half-pixel offset. Map the 11 classes to a cartoon biome palette, and use the DEM (altitude, slope) plus OSM landuse to correct snow/bare/moss confusion and pre-2021 urban gaps.
- OSM acquisition: keep geo2day as primary (it works from cloud CI) and Geofabrik as fallback. Always follow redirects, verify md5, and pin a snapshot by replication timestamp or sequence. Use pyosmium-up-to-date for refreshes instead of full re-downloads. Strip metadata (osmium cat --clean or equivalent) before any data ships.
- Pin pyosmium==4.3.1 and osmium-tool 1.19.x. Write extractors as FileProcessor pipelines with C++ filters (KeyFilter/TagFilter/EmptyTagFilter), using with_locations('flex_mem') and with_areas() only where geometry is needed. Use osmium extract -s smart with the .poly or a bbox to make small dev slices such as the Kathmandu valley.
- Names and search: prefer OSM name:en/name. For Devanagari-only names, generate romanizations offline with aksharamukha (Devanagari to RomanColloquial with RemoveSchwaHindi), or with indic-transliteration plus custom Nepali schwa-deletion rules if AGPL is a concern. Use IndicXlit for Latin-to-Devanagari. Ship only the generated strings, not the AGPL code.
- On-device fuzzy search: precompute normalized search keys in the pipeline (lowercase, strip diacritics, collapse aa/ee/ii/oo/uu, v/w, sh/s/ṣ, chh/ch/c, ph/f, final -a deletion, plus known aliases such as Sagarmatha/Everest and Chitwan/Chitvan). Ship a trigram index and run a small Damerau-Levenshtein in C#. Use rapidfuzz in Python only for pipeline QA and regression tests.
- Put the exact attribution strings in LICENSES and the in-game credits: Copernicus WorldDEM-30 modified-data notice, ESA WorldCover 2021 notice, '© OpenStreetMap contributors' (ODbL), plus any AW3D30/JAXA or Overture credits if those sources are used.
- Record DEM provenance as: 'Copernicus DEM GLO-30 Public, 2021 release (per AWS registry), s3://copernicus-dem-30m, objects 2022-05-09', plus per-tile ETag. CDSE's latest is 2024_1, but no post-2021 release note touches Nepal.
- Select tiles by intersecting nepal.poly plus an explicit horizon buffer (e.g. 30-50 km for Tibetan and Sikkim skylines), not by bbox. That gives 28 GLO-30 tiles (1.18 GB) and 8 WorldCover tiles (0.82 GB), not 45 and 10.
- Fix the WorldCover manifest: drop N24E078 and N24E081 (they do not touch Nepal) and use 124.0 GB (115.5 GiB) as the global v200 Map size.
- Do not plan on WorldCover InputQuality from S3; it is 404 for Nepal tiles. If needed, use the non-S3 delivery channels named in PUM v2.0, or derive quality from other sources.
- Build a DEM-quality layer from EDM/FLM/HEM using the handbook code tables. Run a summit-correction pass wherever EDM=2 near OSM natural=peak nodes with ele: raise a smooth cone or blend to the published height. Every 8000 m summit tested is infilled and 22-242 m too low.
- Handle registration explicitly. GLO-30 COGs are pixel-is-point with centres on integer degrees and dropped south/east edges; WorldCover is pixel-is-area. Resample both to one game grid with documented half-pixel handling to avoid seams.
- LICENSES/credits must carry: (1) the Copernicus Art. 6(b) 'produced using Copernicus WorldDEM-30 ...' notice, (2) the Art. 6(c) liability sentence, (3) the WorldCover 2021 attribution and CC BY 4.0, (4) OSM ODbL attribution. NASADEM, if used, is CC0, but credit NASA/LP DAAC without implying endorsement.
- Keep FABDEM and FathomDEM+ out of shipped builds unless a commercial licence is bought. NASADEM is a licence-safe secondary DEM for QA of GLO-30 infill.
- In the fetch step, verify Geofabrik downloads with the .md5 and record state.txt sequenceNumber and timestamp. Use the nepal-updates diffs (kept 100 days) for incremental refresh.

### Open risks

- GLO-30 is a DSM, not a DTM. Trees and buildings raise the surface around Kathmandu and the forested hills, and FABDEM, the obvious fix, is non-commercial. Building or tree removal would have to be home-grown, e.g. using WorldCover classes 10/50 plus OSM buildings.
- Summits and steep ridges are infilled from older SRTM/ASTER data and run 20-240 m low, with possible seams or terraces. The peak-height errors were measured with approximate coordinates and a ±600 m window and should be re-checked per peak.
- The exact Copernicus release label of the AWS mirror (objects dated 2022-05-09) is unverified. It is probably 2021_1, but the CDSE copy (2024_1) would need credentials to cross-check.
- In this sandbox, direct curl to download.geofabrik.de was reset by peer, cause unknown (proxy or IP block). geo2day is a small independent service with no stated SLA or rate limits, so CI fetching OSM is fragile and a cached mirror is recommended.
- Overture keeps only 60 days of releases. Any Overture-derived data must be mirrored, and ODbL share-alike obligations apply to derived databases.
- WorldCover 2021 is about 5 years old, with no newer version found. Accuracy for snow/ice vs bare vs moss/lichen in the high Himalaya and for cropland/built-up in the Terai is uncertain at 10 m.
- The aksharamukha licence is AGPL-3.0 per PyPI (the GitHub repo shows a GPL-3.0 file). It is safe only as an offline tool, and legal should confirm that generated output is not encumbered.
- Not verified: current ISO 15919 status (iso.org 403), BBBike extract limits (site returned 503), HOT raw-data-api usage limits and freshness, and Cesium for Unity's iOS support (changelog says yes, marketing page omits it).
- The extract polygon reaches 80.049E and 30.25N west of 81E, possibly including disputed areas (Kalapani/Lipulekh/Limpiyadhura). Which country boundary and naming the game shows is a political and legal decision outside the data pipeline.
- The extracts include cross-border features (e.g. Shishapangma in Tibet), so gameplay boundaries need a deliberate clip polygon.
- Repository provenance mismatch: pipeline/data/raw/osm/nepal.osm.pbf (468,147,023 bytes) has an .md5 that references '/var/www/maps/data/www/osmtoday.com/asia/nepal.pbf'. It came from an osmtoday.com mirror, not Geofabrik's 395 MB nepal-latest.osm.pbf (md5 d098ee3d...). Source, size and timestamp claims in docs may not match the data actually used.
- Network from this sandbox: direct curl to download.geofabrik.de and overpass-api.de failed with connection resets through the agent proxy, though WebFetch could read Geofabrik pages. A CI fetch step must be tested on the real runner.
- The WebSearch budget was exhausted during this pass. The check for 2025-2026 Copernicus DEM releases relied on CDSE pages (latest listed 2024_1) and AWS registry text, not a broad web search.
- The FABDEM CC BY-NC-SA 4.0 licence was confirmed only through a secondary catalog (gee-community-catalog) and Fathom's 'commercial license or free for non-commercial use' wording. The University of Bristol data page timed out.
- Reference heights for Makalu (8485 m) and Cho Oyu (8188 m) and their coordinates came from commonly published values, not OSM nodes. Other peaks used the OSM nodes in the repo's landmarks.resolved.json.
- nepal.poly is Geofabrik's slightly buffered clipping polygon, so 28 DEM and 8 WorldCover tiles is an upper bound for the true border. Gameplay horizons (Everest north side, Kangchenjunga/Sikkim) may need extra buffer tiles.
- WorldCover 2021 is 5 years old and no successor is announced. Urban expansion (Kathmandu valley, Pokhara, Terai) and glacier or snow changes since 2021 are not captured.
- The NASADEM 'known high-relief artefacts' assertion is unverified. The Cryosphere 2022 study actually ranked NASADEM best among 30 m DEMs on the Tibetan Plateau, though GLO-30 was not tested.
